2. API keys

  • A key is shown once, at creation. We store only a SHA-256 hash and cannot recover the key for you — if you lose it, create a new one.

3. Scopes

Keys carry explicit scopes — read, orders, sms — and a call outside a key's scopes is refused. Grant each key the narrowest set that its integration actually needs. Do not attempt to access data or endpoints outside your granted scopes.

4. Rate limits and fair use

Each key has a published per-minute limit. Every response returns your current position in the X-RateLimit-* headers, and exceeding the limit returns 429 with Retry-After.

You must respect those headers and back off rather than retrying immediately. Do not run parallel clients to multiply your limit, create extra accounts or keys to evade it, or poll faster than the data actually changes. We may reduce a limit, or suspend a key, where usage threatens service stability for others.

5. Purchases through the API

API purchases spend the wallet balance of the key's owner, exactly as the website and bot do. There is no card flow in the API. You are responsible for every purchase your integration makes — a bug in your code that buys in a loop spends real money, and those purchases are not automatically refundable.

We strongly recommend testing against a small balance first, handling 402 insufficient_balance explicitly, and never retrying a failed purchase blindly.

The API is versioned. Within /api/v1 we aim to make only backward-compatible changes — adding fields or endpoints, never removing or renaming what is already there. Build clients that ignore unknown fields.

11. Support
