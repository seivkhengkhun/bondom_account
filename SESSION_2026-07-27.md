## 2. What this project is

A digital-goods store for the Cambodian market, sold three ways from one
database:

- **Telegram bot** (aiogram) — the original channel
- **Web storefront** (FastAPI + Jinja) — `skshopping.store`
- **Public REST API** `/api/v1` — for third-party integrators

Plus a **Reflex admin panel** at `admin.skshopping.store`, shipped as a
prebuilt static bundle because the VPS CPU lacks AVX and cannot run Bun.

Products are account credentials; there are also rented **SMS
verification numbers** (US, KH, HK) via the Angkor Phone SMS reseller.
Payment is **KHQR through Bakong**; customers hold a **wallet balance**.

## 4. Architecture decisions worth knowing

### Everything goes through the service layer
`shared/services.py` and `shared/payment_service.py` own all business
rules. The bot, storefront, admin panel and API are thin layers over
them. **Enforce rules at the service gate, never only in a UI** — that is
why a crafted POST cannot bypass the `$2` minimum, the per-product
minimum quantity, or the payment throttle.

### `app_settings` is the escape hatch instead of migrations
There is no Alembic. Rather than add columns, per-entity flags live as
key/value rows:

| Key | Meaning |
|---|---|
| `user_balance:<id>` | Wallet balance (**not** a column on the user) |
| `user_blocked:<id>` | Permanent block |
| `user_deleted:<id>` | Soft delete marker, distinct from suspension |
| `topup_override:<id>` | May top up below the `$2` minimum |
| `product_note:<id>` | Delivery note |
| `product_min_qty:<id>` | Minimum order quantity |
| `admin_password_hash` | PBKDF2-SHA256, 210k iterations |
| `sms_markup_usd` | Global SMS markup |

Consequence: deleting a user means deleting their `app_settings` rows
too — the balance is easy to leave behind.

### Order/payment ordering matters
Creating an order allocates stock. If payment creation then fails, the
order strands inventory nobody can pay for. Both the website and the bot
now (a) check the payment throttle **before** allocating stock and
(b) release the order if payment creation raises. Do not reorder this.

### Hard delete is refused for users with orders
`orders.user_id` is `ondelete="RESTRICT"`, but **SQLite has
`PRAGMA foreign_keys = 0`**, so the database will not stop a bad delete.
The rule is enforced in Python. Prefer soft delete — it works for every
user and is reversible.

## 5. Feature reference

- **Admin auth** — PBKDF2 hash in `app_settings`; `ADMIN_PASSWORD` in
  `.env` bootstraps the first login then stops working once a password is
  set in the panel. 15-minute idle auto-logout.
- **Admin panel** — Overview with charts, sortable/filterable tables,
  per-user wallet dialog, soft delete + restore, hard delete, top-up
  override toggle, per-product minimum quantity, activity log.
- **Public API** — `/api/v1`, key auth (`bk_live_…`, stored as SHA-256
  hash only), scopes `read`/`orders`/`sms`, 60 req/min, pagination,
  single error envelope with `request_id`.
- **Developer portal** — `/developer`: key management, usage, request
  log, playground. Docs at `/developer/docs`.
- **Legal** — `/legal`: Terms, Privacy, Cookies, Developer Terms,
  Refunds, Acceptable Use. Content is in templates, editable without
  touching Python. **Not reviewed by a lawyer.**
- **Payments** — KHQR card design on web and in Telegram. QR is error
  correction level H so the centre mark stays scannable (verified by
  decoding the composite with OpenCV).
- **Limits** — `$2` min top-up (per-user override to `$0.01`), `$500`
  max, per-product minimum order quantity, 5 payment requests/min/user
  with a 10s duplicate guard.

## 6. Deploy

⚠ **The VPS web console mangles multi-line pastes** — it joins lines,
which once killed the storefront (`pkill` ran, the restart half did not).
**Give one single-line command at a time.**

```
cd /home/ubuntu/bondom_account && /home/ubuntu/bondom_account/.venv/bin/python scripts/backup_db.py
```
```
cd /home/ubuntu/bondom_account && git pull
```
```
sudo systemctl restart bondom
```
```
sleep 8; curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/
```

**Only if `app/web/admin/admin.py` changed**, also:

```
sudo rm -rf /var/www/bondom-admin/assets
```
```
sudo unzip -oq /home/ubuntu/bondom_account/deploy/admin-frontend.zip -d /var/www/bondom-admin
```
```
sudo fuser -k 8001/tcp; sleep 3
```
```
cd /home/ubuntu/bondom_account/app/web && nohup /home/ubuntu/bondom_account/.venv/bin/python -m reflex run --backend-only --backend-host 127.0.0.1 > /tmp/bondom-admin.log 2>&1 &
```
```
sleep 15; curl -s http://127.0.0.1:8001/ping
```

Notes:
- `rm -rf assets` matters — new bundles have different chunk hashes, so
  stale files otherwise pile up.
- Kill the reflex backend **by port**, not `pkill -f reflex`: it misses a
  process whose command line is `python -m reflex`, and the new one then
  fails to bind and exits 1 while the old code keeps serving.
- Wait for `"pong"` before opening the browser. Loading during boot shows
  a websocket error that Reflex never retries.
- `pip install -r requirements.txt` only when dependencies changed.

## 8. Environment gotchas

- **`BOT_TOKEN` in the local `.env` is the LIVE production bot.** Running
  `main.py` locally hijacks it from real customers. For local storefront
  testing use `python -m uvicorn app.api.main:app --port 8000`, which
  never starts the bot.
- **Rebuilding the admin bundle requires `REFLEX_API_URL`:**
  `cd app/web && REFLEX_API_URL=https://admin.skshopping.store python -m reflex export --frontend-only`
  Without it the build bakes in `localhost` and the deployed panel cannot
  reach its backend. Output lands at `app/web/frontend.zip`; copy it to
  `deploy/admin-frontend.zip`.
- **Never `git reset --hard` or force-push** without asking — the VPS
  procedure forbids it without a fresh backup.
- **Do not test against the live `store.db`.** Use a copy. In particular
  never set an admin password while testing: it revokes the `.env`
  bootstrap and locks the owner out.
- Local Reflex ports 3000/8001 sometimes stay held by orphaned sockets;
  work around with `BACKEND_PORT` / `FRONTEND_PORT` env vars.
- **Static assets are cached hard.** `shop.css` is versioned now, but if
  you add another stylesheet or JS file, version it the same way — see
  `_asset_version()` in `app/webshop/routes.py`.

## 9. Open items, highest priority first

### 9.1 Credential leak in a public repo — STILL NOT FIXED
`Novery_May_28_2026_UID_Pass.txt` is **tracked in git** and the repo is
**public**. 12 lines of `UID|Pass` — sellable inventory credentials
readable by anyone. It is in history, so deleting the file is not enough:
rotate the accounts, `git rm --cached`, gitignore it, and purge history
with `git filter-repo` — or make the repo private as an immediate stop.

Raised every session. Still open.

### 9.2 Bakong token expires 2026-10-03
An expired token previously caused payments to silently report UNPAID. A
startup check or a cron warning at 14 days would turn a silent revenue
outage into a warning.

### 9.3 No audit trail on the money itself
Admin actions are logged, but there is no ledger of balance movements —
you cannot reconstruct why a balance is what it is.

### 9.4 In-process state dies with the process
Payment pollers **and** the payment rate limiter are in-process. A
restart drops in-flight top-up polling (top-ups then need manual
crediting) and clears the throttle. Moving both to the database or Redis
is the same piece of work.

### 9.5 Smaller gaps
- Underpayment on an open KHQR is unhandled — the minimum guards session
  creation, not what the customer actually sends.
- No idempotency on `confirm_wallet_topup` — double-credit risk.
- No Alembic; schema comes from `create_all`.
- Backups live on the same VPS as the database.
- SMS markup is a single global value, but HK costs more than US/KH, so
  margin differs per country by accident rather than by choice.
